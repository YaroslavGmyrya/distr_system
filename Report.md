# SAGA

## Определение
Метод обеспечения согласованности данных в распределенных системах (микросервисах), разбивающий одну большую транзакцию на последовательность локальных ACID-транзакций в каждом сервисе. Если один шаг завершается сбоем, Saga запускает компенсирующие транзакции для отката изменений, обеспечивая конечную согласованность.

## Пример 
Допустим, имеется интернет-магазин, построенный на микросервисной архитектуре. Pipeline для каждого заказа:

Создание заказа -> резервирование товара -> оплата -> доставка

## Проблема
Каждый из шагов выполняет свой микросервис. Но что, если на этапе оплаты пользователь решил отказаться от покупки? При монолитной архитектуре можно было бы разом всё откатить, т.к всё находится в одном месте, но в микросервисной архитектуре так сделать не выйдет. 

## Решение

Эту проблему и решает паттерн SAGA.

SAGA предполагает наличие откатывающего действия, которое может быть исполнено в случае ошибки.

## Виды SAGA
2 типа подхода к SAGA:

Хореография: микросервис, на котором возникает ошибка, отправляет на предыдущий микросервис сообщение, а тот при получении запустит откат.

Оркестратор: предполагается наличие отдельного сервиса, который будет контролировать ошибки и выполнение SAGA

# Вопросы для самопроверки

1. Почему в микросервисах нельзя просто использовать `BEGIN TRANSACTION ... COMMIT` для операций, затрагивающих несколько сервисов?

Сервисы имеют разные базы и процессы. Распределённые транзакции сложные, медленные и плохо масштабируются.

2. В чем разница между Оркестрацией и Хореографией? Какой подход проще для старта, а какой лучше масштабируется?

Оркестрация — есть центральный сервис-координатор. Сложнее на старте. Хорошая масштабируемость.

Хореография — сервисы реагируют на события друг друга. Лучше для старта. Плохая масштабируемость.

3. Что такое "компенсирующая транзакция"? Приведите пример.

Это операция, которая откатывает эффект предыдущего шага. Допустим, удаление записи о заказе из БД.

4. Может ли компенсирующая транзакция завершиться ошибкой? Что делать в таком случае?

Вполне может. В таком случае нужно пытаться выполнить операцию снова. Если ошибка не решается, то нужно вмешательство человека.

5. Что такое "согласованность в конечном счете" (Eventual Consistency)?

Данные между сервисами могут быть временно несогласованы, но со временем синхронизируются через события или очереди.
